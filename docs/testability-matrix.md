# ماتریس شفاف‌سازی: چه چیزی واقعاً به بک‌اند متصل است و چه چیزی نمایشی؟

> پاسخ صادقانه به این سؤال کارفرما: «مشخص کنید کدام قابلیت‌ها در نمونه فعلی واقعاً به بک‌اند و دیتابیس متصل و قابل آزمون‌اند و کدام موارد صرفاً نمایشی هستند.»

## بخش الف — نمونه اولیه فعلی (Next.js + Drizzle در ریشه مخزن)

نمونه فعلی با **Drizzle روی PostgreSQL واقعی (PGlite در توسعه)** کار می‌کند؛ یعنی «فرانت و بک در یک پروسه Next.js». وضعیت دقیق هر بخش:

| قابلیت در نمونه فعلی | وضعیت | توضیح |
|---|---|---|
| صفحه اصلی، دسته‌ها، شهرها، لیست کسب‌وکارها | ✅ متصل به DB | از Drizzle روی PostgreSQL می‌خواند |
| صفحه کسب‌وکار + گالری + مسیریابی | ✅ متصل به DB | داده از DB |
| ثبت‌نام/ورود مالک (رمز عبور) | ✅ متصل به DB | هش رمز + سشن؛ **نه OTP و نه پیامک واقعی** |
| سفارش اشتراک (صفحه پرداخت) | ⚠️ نیمه‌واقعی | رکورد سفارش در DB ثبت می‌شود اما «رسید/تأیید مدیر/شروع و پایان خودکار» در نمونه وجود ندارد |
| پنل مدیریت (کسب‌وکارها، پلن‌ها، گزارش‌ها) | ✅ متصل به DB | عملیات نوشتن واقعی |
| QR کارت | ⚠️ نمایشی | QR سمت مرورگر تولید می‌شود؛ به رکورد کارت در DB متصل نیست |
| کد معرف طراح / پورسانت | ❌ نمایشی | UI هست، منطق پورسانت پیاده نشده |
| جست‌وجوی شعاعی (نقشه/موقعیت) | ❌ نمایشی | فیلتر شهر/دسته واقعی است؛ «فاصله تا من» محاسبه PostGIS ندارد |
| لاگ امنیتی/سوابق مدیریتی | ⚠️ حداقلی | یک ردیف audit ساده؛ ساختار کامل ندارد |
| یادآوری تمدید، پایان خودکار اشتراک | ❌ وجود ندارد | — |

**جمع‌بندی نمونه:** طراحی رابط و مسیر عمومی طبق تأیید شما قابل قبول است؛ اما این نمونه به‌معنای معماری مصوب نیست و باید روی بک‌اند Laravel سوار شود.

## بخش ج — رابط کاربری (فاز F1)

رابط فعلی Next.js به‌صورت نمونه (با لایه داده Drizzle خودش) کار می‌کند و در فاز F1 به‌طور کامل به API لاراول وصل می‌شود. تا آن زمان، معیار پذیرش‌ها **همه سمت API و تست‌های خودکار** تعریف شده‌اند (همان چیزی که در بخش ب قابل آزمون است)، تا پرداخت مرحله‌ای بر مبنای نتایج قابل‌اندازه‌گیری انجام شود.
